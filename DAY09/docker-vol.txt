Docker volumes
docker Networks are used for container communication, Docker volumes are used for storage.
Before Docker volumes
Diagram
Before docker volumes we can store the data in the docker container file system, But If my container crashed or removed then our data will be lossed
To overcome this problem we are going for a docker volumes

What is Docker volume?
Containers are usually temporary; when they stop or restart, any data inside them is lost.
Volumes allow you to store data outside the container, so it persists even after the container is gone.

1. Bind mount
  It will connect a folder from your host machine to a folder inside the container.
  So, whatever data the container writes will be stored in your host system.
  By using bind mount we can store data in the server file system, Eventhough our container crashed, we will recover the data.
2. volumes
  (i) local volumes
  This is the default volume type in Docker.
  Data is stored in this path: /var/lib/docker/volumes/
  Useful for local development and even production.
  Easy to backup and restore.
  Docker handles everything (no need to create the folder yourself).
  (ii) network volumes [NFS,EBS,S3]
  Used when containers are running in different servers or clusters (like in cloud or Kubernetes).
  Examples: AWS EBS, NFS mounts, S3 buckets
  Good for big production setups, not required in normal Docker practice.

Why You Must Care About Docker Data Persistence
Imagine you're running a Spring Boot application inside Docker. The app is working well, allowing
you to register users and store their data in MongoDB.
Now suddenly one day ... your MongoDB container crashes
You start it again ... but all the data is gone
This happens because Docker containers are temporary. That means, when the container is
deleted, the internal storage (file system) inside the container will also be removed.

So, unless we do proper setup for saving data outside the container, everything will be lost if
container stops or crashes.
How to Stop This Data Loss in Docker?
Docker gives us two powerful options to save our data outside the container:

Bind Mounts
. It will connect a folder from your host machine to a folder inside the container.
. So, whatever data the container writes will be stored in your host system.
. Even if container is removed, data is still safe in your system folder.

Docker Volumes
1. Local Volume

. This is the default volume type in Docker.
. Data is stored in this path: /var/lib/docker/volumes/
. Useful for local development and even production.
. Easy to backup and restore.
. Docker handles everything (no need to create the folder yourself).

2. Remote or Network Volume (NFS, EBS, S3)
. Used when containers are running in different servers or clusters (like in cloud or
Kubernetes).
. Examples: AWS EBS, NFS mounts, S3 buckets
. Good for big production setups, not required in normal Docker practice.

In this guide, we will take a real project (Spring Boot + MongoDB), and we will simulate data
loss first, then we will solve it using Bind Mounts and Docker Volumes.

Why Data Is Lost?
Remove the container again, and this time we will use volumes and mounts:
Because you did not use a volume or bind mount to persist MongoDB data outside the container.
When a container is removed, its internal storage (including your users collection) is deleted too.

. /data/db is the default data path inside MongoDB container.
. Your host path: /home/ubuntu/spring-boot-mongo-docker-kkfunda/mongo-bkp

2. Start MongoDB with Bind Mount
Now that both containers are running:
. MongoDB is running with a bind mount for persistent data.
. Spring Boot app is running and connected to MongoDB via environment variables.

Solution 2: Docker Volumes
Step 1: Create Docker Volume
We first create a Docker-managed volume named jiovolume.
docker volume create jiovolume
docker volume ls
Step 2: Remove Old Mongo Container (If Running)
docker rm -f mongo
. This removes the existing Mongo container so that we can run a new one with the volume
attached.
Step 3: Run MongoDB with Volume
Now let's run a new MongoDB container using the volume jiovolume for storing its database files:
All data now goes into the volume jiovolume.
docker run -d -- name mongo -v jiovolume:/data/db -- network jio -e
MONGO_INITDB_ROOT_USERNAME=devdb -e MONGO_INITDB_ROOT_PASSWORD=dev@123 mongo

Step 4: Register Users in Your Application
. Register a few users using the web UI. These user records are stored in MongoDB, and
because we used a volume, the data will be safe even if the container crashes.
Step 5: Simulate a Crash (Delete Container)
Now let's assume a crash happens. We'll manually delete the MongoDB container:
docker rm -f mongo
Remember: containers are removed, but volumes are not affected.
Step 6: Recreate Mongo Container Using the Same Volume
Now run MongoDB again, using the same volume as before:
docker run -d -- name mongo -v jiovolume:/data/db -- network jio -e
MONGO_INITDB_ROOT_USERNAME=devdb -e MONGO_INITDB_ROOT_PASSWORD=dev@123 mongo
Now open your application again and check all the user data is still there!
. Because the data was not stored inside the container, but inside the Docker volume
(jiovolume), which lives outside the container. Even after deleting and recreating the
container, the data persisted.

Docker Objects

Summary of Docker Objects
- **Containers**: Running instances of images.
- **Images**: Read-only templates used to create containers.
- **Volumes**: Persistent storage for container data.
- **Networks**: Facilitate communication between containers and external systems.
- **Registries**: Storage and distribution points for images.
- **Dockerfile**: Defines how to build a Docker image.
- **Docker Compose**: Manages multi-container Docker applications.

What is Docker Build Context?
In Docker, the **build context** is the set of files and directories that are available to the Docker engine when building a Docker image. 
The build context includes the `Dockerfile` and any files required for the image build process.

1.What is Docker Architecture?
Docker Architecture is the system design behind Docker.
It shows how Docker works to create, run, and manage containers efficiently.
Docker Architecture Contains Three Components:
1. Docker Client
2. Docker Host
3. Docker Registry

1.1 Docker Client
Provides CLI (Command-Line Interface) commands
When a user enters a Docker command (e.g., docker run docker build docker pull), the Docker
Client sends an API request to the Docker Daemon (inside Docker Host). The Docker Daemon
istens for these requests from the Client and executes them, managing container operations as
needed.
1.2 Docker Host
The Docker Host is the machine (or environment) where the Docker Daemon and other
components like Docker images and containers are managed and executed. It's one of the
main components of Docker's architecture.
What the Docker Daemon Does:
The Docker Daemon is the core service inside the Docker Host.
It listens for API requests from the Docker Client and performs key actions like:
1. Waiting for Instructions
The Docker Daemon waits for commands from the Docker Client via API requests.
2. Building Images
It builds Docker images from Dockerfiles (files that define the image content).
3. Starting and Running Containers
It uses the images to create and start containers - containers are like live, running
apps made from the images.
4. Managing the Full Lifecycle of Containers
The Docker Daemon manages containers through all their stages:Start,Stop ,Delete
Inside the Docker Host
The Docker Host is like a working environment where everything happens.
Inside the Docker Host, there's a background service called the Docker Daemon (dockerd).
This service handles all container-related tasks, such as:
. Running containers
. Storing Docker images
. Handling container networks (so containers can talk to each other)
. Managing volumes (saving container data)
Example : The Docker Host is the kitchen, and the Docker Daemon is the chef that prepares
the containers (like food) based on the recipes (Docker images).

1.3. Docker Registry
A Docker Registry is a central place where Docker images are stored and managed.
It allows you to push (upload) and pull (download) images as needed.
Two Types of Registries:
1. Public Registry:
o Example: Docker Hub
o Open to the public, commonly used for sharing and accessing images.
2. Private Registry:
o Example: Docker Trusted Registry
o Secure and used mainly within organizations for storing private images.
. This is where Docker images are saved.
. If your system doesn't have the image, it pulls (downloads) it from here.

2. Docker Workflow
Dockerfile - Docker Image -> Docker Container
. Dockerfile: A Dockerfile is a blueprint that contains a set of instructions to build a Docker
image. It defines the steps, environment, and dependencies needed for your application.
. Docker Image: A Docker image is a read-only snapshot of your application's environment
at a specific point in time. It contains everything needed to run an application, including the
code, libraries, and system tools.
. Docker Container: A Docker container is a running instance of a Docker image.
It's mutable (can be changed during runtime) and isolated from other containers and the
host system. Containers allow applications to run consistently across different environments.
Client → API Request → Docker Daemon (on Host) → Check Image Local → 
If Not Found → Pull from Registry → Create Container → Start Container

11.Removing Docker Images
Normally, to remove a single Docker image, you use:
docker rmi (or) < image name>
To Remove All Images at Once:
You can use:
docker rmi $(docker images -aq)
Explanation:
. docker images -aq -> lists only image IDs.
. $( ... )- passes those IDs into the docker rmi command.

Common Mistake:
docker rmi (docker images -aq)
This fails with a syntax error because Bash doesn't use parentheses () for command substitution
- it uses $().

13. Real-World DevOps: Build Server + Deployment Server
Workflow
So far, we've done everything - building the Docker image, tagging, and running the container on
a single server.
But in real-world DevOps, we follow a cleaner and more scalable setup using two different
servers:
1. Build Server (CI or Development Environment)
This server is responsible for:
. Building Docker images from the source code
. Tagging images with version numbers
. Pushing them to a remote Docker registry (like Docker Hub or private registry)

Example:
docker build -t kkeducation1234/javawebapp:1.0.0.
docker push kkeducation1234/javawebapp:1.0.0
This server is usually connected to CI tools like Jenkins, GitHub Actions, or GitLab Cl, which
automatically build the image when code changes are pushed.

2. Deployment Server (Staging or Production)
This server is not involved in building. It's meant only for running the container.
. Pulls the image from Docker Hub (or other registry)
. Runs the image as a container to serve the app
Example:
docker pull kkeducation1234/javawebapp:1.0.0
docker run -d -p 8080:8080 kkeducation1234/javawebapp:1.0.0
You don't need to copy code or build files here - just pull the ready-to-use image and deploy it.
Deployment Server Setup

2. Install Docker on the deployment server

16. Docker Tag - Naming and Versioning Images
The docker tag command is used to give a new name or version to an existing image.
It's similar to how you use the mv command in Linux to rename a file, but here you are tagging an
image (not moving it).
docker tag:
docker tag kkeducation12345/javawebapp:1.0.0 kkeducation12345/javawebapp:2.0.0
It creates another reference (alias) to the same image ID. You're not copying or modifying the
image - just giving it a new label.

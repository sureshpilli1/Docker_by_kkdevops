What is Docker?
Docker is a containerization platform that allows developers to package applications and their dependencies into a standardized unit called a **container**. 
This ensures consistency across different computing environments and improves efficiency in application deployment and scaling.  
Similar Tools to Docker:
- **Podman**  
- **Rkt (Rocket)**  
- **LXC (Linux Containers)**  
- **Singularity**  

Docker Editions:
1. **Community Edition (CE):** Open-source and free to use.  
2. **Enterprise Edition (EE):** Commercial version with advanced security and support features.  

**Vendor:** Docker Inc.  
**Type:** Containerization  

Related Technologies:
- **SCM Tools:** Git  
- **Build Tools:** Ant, Maven, Gradle  
- **CI/CD Tools:** Jenkins, Bamboo, Travis CI  
- **Containerization Tools:** Docker, Podman, Rkt  

**Cross-Platform:** Docker is supported on Linux, Windows, and macOS.

Installing Docker
**Official Website:** [https://www.docker.com/](https://www.docker.com/)  
**Documentation:** [https://docs.docker.com/](https://docs.docker.com/)  
Installation Steps (Ubuntu EC2 Instance):
1. **Create an EC2 instance** (Ubuntu-based)  
2. **Connect to the server** using SSH  
3. **Install Docker using one of the following methods:**  

Method 1: Using Docker’s official script  
```sh
sudo apt update -y
sudo curl -fsSL https://get.docker.com -o install-docker.sh
sudo sh install-docker.sh
```
Method 2: Installing from Ubuntu Repository  
```sh
sudo apt update -y
sudo apt install docker.io -y
```
Method 3: Running Docker’s install command directly  
```sh
sudo apt update -y
sudo curl -fsSL https://get.docker.com | /bin/bash
```

4. **Verify installation**  
```sh
docker -v
```

5. **Check Docker service status**  
```sh
ps -ef | grep -i "dockerd"
sudo service docker status
```

6. **Fix Docker permission issues**  
```sh
sudo usermod -aG docker ubuntu
```
**(After this, log out and log back in for changes to take effect.)**  

7. **Confirm that Docker runs without sudo**  
```sh
docker ps
```

## Docker Architecture

![Docker Architecture](../images/docker-architecture.png)

1. Docker Engine
**Docker Engine** is the core component responsible for building, running, and managing containers. It consists of:  
- **Docker Daemon (dockerd):** Runs in the background, manages containers, images, and networking.  
- **Docker API:** Enables interaction between the daemon and the Docker CLI or other programs.  

2. Docker CLI (Command-Line Interface)
The CLI allows users to interact with Docker. Common commands include:  
```sh
docker run
docker build
docker ps
docker images
```

3. Docker Images
Docker images are the templates used to create containers. They are:  
- **Immutable** (cannot be modified once built)  
- **Layered** (built from multiple layers for efficiency)  
- **Version-controlled**  

4. Docker Containers
Containers are lightweight, portable, and run applications in an isolated environment.  
- Share the host OS kernel but have separate filesystem, processes, and network.  
- Created from Docker images using `docker run`.  

5. Docker Registry
A registry is a centralized storage system for Docker images.  
- **Public Registry:** Docker Hub (default)  
- **Private Registries:** Nexus, JFrog Artifactory, AWS ECR  

---

Managed Docker Registries

- **AWS ECR (Elastic Container Registry)** – Amazon’s managed registry for AWS  
- **Azure ACR (Azure Container Registry)** – Microsoft Azure’s container registry  
- **GCP GCR (Google Container Registry)** – Google Cloud’s registry  

Docker Repository
A Docker **repository** is a collection of images with the same name but different tags (versions).

NOTES FROM BLOG:
---------------

Docker is an open-source containerization platform.
It allows you to package an application along with all its dependencies into a single, isolated
unit called a container.
With Docker, developers can easily build, run, and manage applications across different
environments without worrying about compatibility issues.
Unlike virtual machines, Docker containers share the host system’s kernel, making
them lightweight, portable, and faster.
This makes Docker ideal for running applications consistently on any system — whether it’s your
laptop, a server, or the cloud.

What is a VM (Virtual Machine)?
A Virtual Machine (VM) is software that behaves like a separate physical computer.
It runs its own operating system (OS) and applications, but inside a host machine using
a hypervisor like VMware, Oracle VirtualBox, or Microsoft Hyper-V.
Each VM gets its own dedicated memory (RAM), CPU, and storage, even though it’s all coming
from the same physical system.
Virtual Machine (VM) vs Docker Memory Usage (with 16GB Example)
Using Virtual Machines (VMs):
You have 3 VMs:
• VM1 – allocated 6 GB (actually using 4 GB, 2 GB free inside VM)
• VM2 – allocated 4 GB (using 3 GB, 1 GB free)
• VM3 – allocated 6 GB (using 2 GB, 4 GB free)

Total allocated = 6 + 4 + 6 = 16 GB
Actually used = 4 + 3 + 2 = 9 GB
Free (unused inside VMs) = 7 GB

Problem with VMs:
Even though 7 GB is free inside the VMs, the hypervisor has already reserved all 16 GB.
That means, from the host system’s perspective, the full memory is occupied.
You can’t launch another VM unless you shut down or reduce memory from existing VMs.
That 7 GB free is not shareable outside its VM.

Using Docker Containers:
Let’s say you run 3 containers with memory limits:
• Container1 – max 6 GB, but currently using 4 GB
• Container2 – max 4 GB, using 3 GB
• Container3 – max 6 GB, using 2 GB
Total memory in use = 4 + 3 + 2 = 9 GB
Free memory on host = 16 GB - 9 GB = 7 GB
Advantage with Docker:
The remaining 7 GB is fully available to launch more containers or for other system needs.
Memory is dynamically shared — what one container doesn’t use, others can.
• In Docker, free memory is still usable, and you can start more containers.
• In VMs, once memory is reserved, even unused RAM can’t be shared.

Why the Shift from VMs to Docker?
Software development has rapidly evolved over the past decade.
One major shift has been moving from Virtual Machines (VMs) to Docker containers for
deploying applications. Why?
• Faster development & deployment cycles
• Smaller, more efficient resource usage
• Solving the “it works on my machine” problem
• Easier version and dependency management
Let’s break down the “Before Docker” vs “After Docker” deployment and explore why Docker
became a game-changer.
Before Docker: Traditional VM-Based Deployment
How It Worked (Old Way)
• Developers write code on their local machines (Dev).
• Code is manually deployed to QA, then Staging, then Production.
• Each environment has different configurations.
• Applications run inside Virtual Machines (VMs) like VirtualBox or VMware.
• VMs contain full operating systems, making them heavy and slow.

Common Problems
• Version mismatch: Java 17 on Dev, Java 8 on Prod → app crashes.
• Heavy resource usage: VMs can take up several GBs of RAM and disk.
• Slow startup times: VMs can take minutes to boot up.
• Difficult to reproduce environments: Each stage needs manual setup.
• Dependency conflicts: Apps can overwrite each other’s ports or system files.

After Docker: Modern Containerized Deployment
How It Works (New Way)
• Developers write code and a Dockerfile that defines the app’s environment.
• A Docker image is built — self-contained and version-controlled.
• The same image is deployed to Dev, QA, Staging, and Production.
• Apps run inside Docker containers, which are lightweight and isolated.
Key Benefits
• Consistent environments: One image works the same everywhere.
• Lightweight & fast: Containers use less RAM and start in seconds.
• No version issues: You choose exactly which Java/Python/MySQL version is used.
• Better isolation: No more conflicts between apps.
• Easier CI/CD: Build the image once, deploy it anywhere — automatically.

Does Docker Handle Versions Automatically?
No, it doesn’t. But it gives you full control.
What Docker does not do:
• It doesn’t automatically pick versions for you.
• It won’t fix version problems by itself.
What Docker does give you:
You can set the version yourself in the Dockerfile.

FROM openjdk:17
This means: “Use Java 17 for this app — always.”
The best part?
You don’t need to install Java or Python on your server or laptop.
Docker will pull the correct version inside the container.
You can even run Java 8, Java 11, and Java 17 apps at the same time — no problem, no conflict.
Same image everywhere:
• You build the Docker image one time.
• Then use the same image in Dev, QA, and Production.
• This keeps everything consistent and simple.

Conclusion:
• Docker doesn’t magically fix version issues.
• But if you set things correctly, Docker makes sure your app runs exactly the same
  everywhere.
• No more crashes.
• No more “it worked on my laptop but not in Prod.”
• No need to reinstall Java or Python again and again.

Why does this happen?
Docker has two major pieces to understand:

docker commanD
     ↓
Docker daemon
     ↓
Containers
The Docker daemon (dockerd) normally runs with root-level privileges.
The normal Ubuntu user may not initially have permission to communicate with it through:
/var/run/docker.sock
Therefore:
docker info
may produce:

even though Docker is correctly installed.

Docker installed
You can check:

sudo service docker status
Both are useful checks.

11. Step 6 — Add the current user to the Docker group
The document shows:
sudo usermod -aG docker ubuntu
This is intended to allow the ubuntu user to execute Docker commands without typing sudo every time.
Breaking it down
sudo
 ↓
administrator privileges
usermod
 ↓
modify a user

-a
 ↓
append

-G docker
 ↓
add user to docker group

ubuntu
 ↓
the user being modified

So:
sudo usermod -aG docker ubuntu
means:
Add the ubuntu user to the docker group without removing the user's existing supplementary groups.
Why is the Docker group important?
Before adding the user:
ubuntu$ docker info
        ↓
Permission denied

After adding the user to the Docker group:
ubuntu$ docker info
        ↓
Docker daemon
        ↓
Works without sudo

You may need to log out and log back in (or start a new session) for the new group membership to take effect.
Then you can use:
docker ps
instead of:
sudo docker ps
One important security point
Membership in the docker group effectively provides very powerful control over the Docker daemon and therefore the host. So it should not be treated as a harmless ordinary group.


Step 7: Run Docker commands without sudo
Earlier, you ran:
sudo usermod -aG docker ubuntu
This added the ubuntu user to the docker group.
But the change does not immediately apply to your current terminal session.
That's why the note at the top says:
You must log out and log back in (or restart the session).
Why?
When you logged in, Linux created your session with a particular set of group memberships.
For example, before:
ubuntu
 ├── ubuntu group
 └── other groups
After running:
sudo usermod -aG docker ubuntu
the user's account is changed to:

ubuntu
 ├── ubuntu group
 ├── other groups
 └── docker group  ← added

But your already-open terminal session doesn't automatically reload those groups.
So you log out and log back in.
Then the new session knows:
ubuntu → member of docker group

can be executed without sudo.

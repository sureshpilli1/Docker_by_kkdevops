8. ENTRYPOINT
-------------
--> CMD instruction used to execute a commands/ scripts etc.
--> RUN instruction will be exuecuted while creating an image.
-->  ENTRYPOINT instruction used to execute a commands/ scripts etc.

EX: ENTRYPOINT java -jar app.jar  --> shell form
    ENTRYPOINT ["java", "-jar", "app.jar"]--> executable form

IQ] what is the difference between CMD and ENTRYPOINT?
ANS:

  --> CMD instructions are overriden while creating a container, But ENTRYPOINT instructions can't be overrriden while creating a container.
  --> Both the instructions are used to start our container.

IQ] can we keep both CMD and ENTRYPOINT instructions in a Dockerfile?
Ans: Yes, But CMD instructions will not be executed if both are present, CMD instructions will be passed as an argument to the ENTRYPOINT.

  EX: CMD ["ls"]
      ENTRYPOINT ["echo", "Hello"]

    --> It will be executed as below:
       
        /bin/echo Hello ls

       output: Hello ls

scenario: Our requirement always we have to execute sh catalina.sh, But argument by default it has to execute "start"

       Ex: CMD ["start"]
           ENTRYPOINT ["sh","catalina.sh"]

      /bin/sh catlina.sh start

Docker build cache is a mechanism Docker uses to reuse results from previous docker build commands instead of doing the same work again.
This makes Docker image building much faster.

FROM ubuntu:24.04
RUN apt update && apt install -y nginx
COPY app.py /app/app.py
CMD ["python3", "/app/app.py"]

The first time you build:
docker build -t myapp .
Docker has to execute everything:
FROM ubuntu
   ↓
RUN apt update + install nginx
   ↓
COPY app.py
   ↓
CMD
   ↓
Image
Docker stores the results of these steps in its build cache.
Now you change app.py

You run:
docker build -t myapp .
Docker checks each Dockerfile instruction.
It may do:
FROM ubuntu:24.04
       ↓
    CACHE HIT ✅
       ↓
RUN apt update && apt install nginx
       ↓
    CACHE HIT ✅
       ↓
COPY app.py
       ↓
    changed ❌
       ↓
execute COPY again

So Docker doesn't reinstall nginx again.
That's the main benefit of the cache.
Docker tries to reuse each previous build layer if nothing relevant has changed.
Once a particular step needs rebuilding, later steps generally need to be rebuilt as well.

Why Dockerfile order matters
Consider this:
Bad order
COPY . .
RUN pip install -r requirements.txt
If you change any application source file, the COPY . . layer changes, which can invalidate the cache for the following RUN pip install.
Better order
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
Now if you only change:
app.py
Docker can reuse:
COPY requirements.txt
      ↓pip install
      ↓
CACHE HIT ✅

and only redo:
COPY . .
This makes builds much faster.
You may see this during docker build
For example:
[1/5] FROM ubuntu:24.04
 ---> Using cache
[2/5] RUN apt update
 ---> Using cache
[3/5] COPY requirements.txt .
 ---> Using cache
[4/5] RUN pip install -r requirements.txt
 ---> Using cache
[5/5] COPY . .
When you see:
Using cache
Docker is saying:
"I already performed this build step before, and I can reuse the previous result."
Easy way to remember
First build
Dockerfile
   ↓
Execute steps
   ↓
Store results in cache
   ↓
Image

Next build
Dockerfile
   ↓
Check previous results
   ↓
Can I reuse this step?
   ↓
YES → CACHE HIT → reuse it ⚡
NO  → execute again
So Docker build cache = saved results of previous image-build steps that Docker can reuse to avoid repeating work.

9. ARG instruction
-------------------
. Defines variables that are only available during the build process and can be used to pass
build-time arguments.
. Special Feature: It's the only instruction allowed before the FROM instruction in a
Dockerfile.
. You can define multiple arguments in a Dockerfile using ARG. These arguments can be used in
other instructions during the build.
. Important Notes:
O ARG values are only available during build time.
o After the image is built, the values of ARG are not accessible inside running containers.


-->Using the ARG we can define arguments for Dockerfile. we can use these in another instruction.
--> you can define multiple arguments in a Dockerfile
--> ARG the only instruction that may precede FROM in a Docker file.
--> ARG values are not available after building an image, i.e Running container won't access the ARG values.

EX: ARG branchName=development
    ARG environment=prod
    LABEL branch $branchName
--> while creating an image we can pass ARG as below
    ARG baseImageTag
    FROM debian:$baseImageTag
    docker build -t <imageName> --build-arg  baseImageTag=12.0 .
Example :

FROM debian:$baseImageTag
MAINTAINER KKFUNDA <kkeducationblr@gmail.com>

11. WORKDIR
------------
. WORKDIR sets the working directory inside the container for any following instructions
like RUN, CMD, COPY, or ADD.
. It's like using the cd (change directory) command in Linux.Key Features:
. If the directory does not exist, Docker will automatically create it.
. It helps avoid using full paths in every command.
. You can set multiple nested WORKDIRs, and Docker will build the entire path.

# Base image with Tomcat
FROM tomcat:9.0
# Set working directory to Tomcat's webapps folder
WORKDIR /usr/local/tomcat/webapps/myapp
# If '/usr/local/tomcat/webapps/myapp' does not exist, Docker creates it.
# If it already exists (e.g., from base image), Docker just enters it.
# Copy the WAR file into the working directory (now inside /webapps/myapp)
COPY target/web-app.war .
# You can run installation or setup commands here if needed
# RUN some-setup.sh
# Start Tomcat (already default, but added for clarity)
CMD ["catalina.sh", "run"]
Here, all operations happen inside /app directory in the container.
Why Use WORKDIR?
. Makes your Dockerfile cleaner and easier to read
. Improves maintainability by avoiding repeated path usage
. Helps with layer caching, as each WORKDIR creates a stable build step.



 
EX:

FROM debian:12.0
MAINTAINER KKFUNDA <kkeducationblr@gmail.com>
LABEL author="kkfunda"
LABEL email="kkeducationblr@gmail.com"
RUN echo "welcome to kkkfunda"
#COPY test.sh test.sh
RUN mkdir -p /opt/app
WORKDIR /opt/app
RUN apt update -y
RUN apt install git wget -y
RUN mkdir -p /opt/test
WORKDIR /opt/test
RUN echo "welcome to kk devops"
COPY abc.txt abc.txt


12. USER Instruction
. Sets the user that runs the container's processes.
. Helps improve security by avoiding running as the root (admin) user.
. You can create a custom user with the RUN instruction and then switch to it using USER.
# Start from official Tomcat base image
FROM tomcat:9.0
# Set working directory
WORKDIR /usr/local/tomcat/webapps
# Copy your WAR file into the container
COPY target/web-app.war .
# Create a user named 'kkfunda' with home and bash shell
RUN useradd -ms /bin/bash kkkfunda
# Give permission to 'kkfunda' user for the webapps directory
RUN chown -R kkfunda:kkfunda /usr/local/tomcat/webapps
# Switch to 'kkfunda' user
USER kkfunda
# Start Tomcat server
CMD ["catalina.sh", "run"]
Running container as normal user (not root) is safer - if someone hacks it, they can't damage
your full system.
Creating Users in Docker: Full vs Basic

Option 1: Full User Setup (Recommended)
RUN useradd -ms /bin/bash appuser
. -m: Creates a home directory for the user (/home/appuser)
. -s /bin/bash: Sets the login shell to Bash
This is better if your app or scripts expect:
. A proper user environment
. The use of ~ (home directory)
. A shell like Bash for running commands

Option 2: Minimal User Setup (Lightweight)
RUN useradd appuser
. Creates a user named appuser
. No home directory
. No shell configured
. Good for lightweight containers
. Works fine if your app doesn't rely on user-specific settings or shell access

13. EXPOSE Instruction
. Declares the port on which the container's app will listen.
. It's informational - it doesn't actually publish the port, but it documents it for users or
tools.
. You declare one or more ports that your containerized app uses.
. To make the port accessible from outside, use -p or -- publish when running the container.
Example:
# Expose port 8080 for Tomcat
EXPOSE 8080
# Start Tomcat server
CMD ["catalina.sh", "run"]
# Expose port 8080 for Tomcat
EXPOSE 8080
# Start Tomcat server
CMD ["catalina.sh", "run"]
Running the container:
docker run -d -p 8081:8080
-- name tomcat tomcat:latest
This maps your host's port 8081 to the container's port 8080.
